## Context

Publishing to the broker directly from the [[service|product-api]] request path creates a dual-write problem: if the database commit succeeds but the broker publish fails, the catalog and its consumers drift out of sync.

## Decision

The Product API writes every product change **and** a corresponding row in an `outbox` table inside a single database transaction in the [[container|product-database]]. A separate relay, the [[service|product-search-publisher]], reads unpublished outbox rows and publishes them to the broker.

## Consequences

- Events are never lost and never published for a change that rolled back.
- Consumers must be idempotent, since delivery is at least once.
